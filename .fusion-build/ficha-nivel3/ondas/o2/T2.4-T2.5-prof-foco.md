## T2.4 — Progressão de proficiência de conjuração

**Achado:** `stepCharSpellcasting` (`systems/pf2e/src/derivations/spellcasting.ts`) lia
`system.proficiency` direto do item `spellcastingEntry` e nunca aplicava
`proficiencyUpgrades[]` da classe concedente — o rank ficava congelado no nível 1 para
sempre. Confirmado por grep: nenhum consumidor de `proficiencyUpgrades` existia em
`spellcasting.ts` (só em `character.ts`/`build.ts`/`elementalBlast.ts`, para outros stats).

**Fix:** adicionei `resolveEntryClass` (mesmo mecanismo de `spellcastingLevels.ts`'s
`resolveEntryClass` — `flags.fusion.classKey`, com fallback para a única classe
conjuradora quando ausente) e `effectiveSpellcastingRank` (mesmo padrão de
`effectiveRank`/`effectiveClassDcRank` já usados por
saves/perceção/armas/armaduras/classDC). `reads` do step ganhou `system.build` (agora lê
`resolveClassLevels`).

**Por que não muda número nenhum no recorte 1-3:** verificado no dado real (Bard,
`classes-core/documents.json`): a primeira linha `stat: "spellcasting"` da tabela de
upgrades só chega no **nível 7**. O gate desta fatia (nível 1-3) fica sem regressão
observável — mas o consumidor passa a existir e é coberto por teste (2 casos novos:
upgrade dentro do nível aplica, upgrade acima do nível não aplica).

## T2.5 — Pool de foco

**Achado real (diferente do que a nota do orquestrador sugeria):** os `rules: []` das
features "Composition/Bloodline/Devotion/Revelation Spells" **também estão vazios no
vendor real** (Foundry pf2e) — não é uma lacuna de curadoria nossa. A entrada
`spellcastingEntry` de foco (`system.isFocusPool: true`) **já é criada genericamente**
por `planVM.ts`'s `hasFocusFeature`/`buildFocusEntryOp` para toda classe com feature de
nível 1 terminada em `" Spells"` — auditei as 29 classes contra `classes-core` e são 7:
Bard, Champion, Magus, Sorcerer, Oracle, Summoner, Necromancer. O defeito real
(confirmado por grep: `isFocusPool` nunca era **lido** em lugar nenhum) é que
`system.resources.focusPoints.max` ficava congelado no default de schema (`0`) para
sempre — a entrada existia, o pool nunca acendia.

**Fix:** `stepCharFocusClamp` (`build.ts`) agora conta as `spellcastingEntry` com
`isFocusPool: true` do ator e combina via `Math.max` com o que já estava persistido
(nunca soma — o campo não é append-only; recalcular por soma dobraria o valor a cada
passada de derivação), antes do clamp de 3 pontos que já existia. Testado idempotente
(2 passadas seguidas não acumulam) e testado contra o teto de 3 mesmo com 4 entradas.

**Decisão registrada (não pedida ao Alexandre, indisponível, decidida pelo código +
regra do PF2e):** `value` **não** é preenchido para o novo `max` quando o pool cresce —
é recurso que o jogador gasta e nada mais escreve nele hoje; auto-preencher aqui seria
adivinhar se um `value: 0` persistido é "nunca concedido" ou "gasto até zero" (postura
"nunca adivinha" já seguida no resto do arquivo — ver `sorcererBloodline.ts`). Um Bard
recém-criado hoje mostra **0/1**, não 1/1. Registrado como pendência abaixo.

## Pendências para issue

**Repo: `xansde/fusion-systems-2e` — ABERTA: https://github.com/xansde/fusion-systems-2e/issues/111**

Título: `focus points: value não enche para o novo max quando o pool é concedido pela
primeira vez`

Corpo:
```
stepCharFocusClamp (systems/pf2e/src/derivations/build.ts, T2.5) deriva
system.resources.focusPoints.max a partir das spellcastingEntry com
isFocusPool:true, mas NUNCA escreve em .value além de clampá-lo para baixo
(min(value, max)). Um personagem recém-criado com uma classe focus-caster
(Bard, Champion, Magus, Sorcerer, Oracle, Summoner, Necromancer) fica com
focusPoints = {value: 0, max: 1} em vez de {value: 1, max: 1} — o pool
"existe" mas aparece vazio na ficha.

Não dá para resolver isso só na derivação sem adivinhar: nada mais escreve
em `value` hoje, então um `value: 0` persistido é indistinguível entre
"nunca concedido" e "jogador gastou até zero" — a derivação roda em toda
atualização do ator, não só na criação.

Fix sugerido: planVM.ts's buildFocusEntryOp (chamado por applyClass) deveria
enviar um doc:update companion setando system.resources.focusPoints.value
= max no MOMENTO da concessão (client sabe que é uma criação nova, a
derivação não sabe). Alternativa: um flag "primeira concessão" no doc que a
derivação possa ler sem adivinhar.

Achado durante ficha-nivel3 Onda 2, T2.5.
```
